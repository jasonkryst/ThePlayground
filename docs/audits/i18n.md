# Internationalization Audit — The Playground

**Date:** 2026-09-04
**Version:** 1.1.10
**Scope:** `src/i18n/`, every `src/games/*/i18n/`, locale-switching UX, hardcoded-string surface, date/number formatting, audio/emoji localizability, CI validation. Read-only audit — no source was modified.

---

## Executive Summary

The Playground is **already multi-locale-ready today**, not merely scaffolded. Three locales ship in production — `en`, `es`, `pl` — across both the core bundle (`src/i18n/*.json`) and all nine per-game i18n folders, with **zero missing keys and correct CLDR-complete pluralization** (Polish's four plural categories — one/few/many/other — are fully populated and unit-tested; English/Spanish's two are as well). Locale switching is live: changing the admin dropdown calls `i18n.changeLanguage()` through the same `useSettings()` broadcast mechanism CLAUDE.md documents for cross-component sync, and it visibly reaches every mounted consumer, including `LocaleSync` itself. A dedicated speech-synthesis hook (`useSpeech.js`) maps locale to the correct BCP-47 voice tag (`en-US`/`es-US`/`pl-PL`) for the two games that speak prompts aloud. Cross-locale key parity and Polish plural-form completeness are enforced by an automated Vitest suite (`src/i18n/__tests__/i18n.test.js`) that runs in CI.

The gaps are narrow and concrete: **four hardcoded English strings in `src/App.jsx`** (the app's top-level loading/error fallbacks, hit on every route transition and on any bad game URL — arguably the most-frequently-rendered untranslated text in the app), a locale-unaware date formatter in the parent dashboard's charts (hardcoded `M/D` instead of `Intl.DateTimeFormat`), an inconsistent fallback in `ScoreHistory.jsx` that drops locale on one code path, no RTL/`dir` support anywhere (untested need, since only LTR scripts are shipped), and no automated lint rule to catch a future hardcoded string the way `App.jsx`'s were missed. None of these undermine the architecture; they're the kind of gaps that accumulate around a genuinely well-designed system when a few spots (notably the router shell, which predates or sits outside the per-game convention) don't get the same discipline as everything downstream of it.

**Bottom line:** this is a real, working three-locale i18n system with sophisticated pluralization and live-switching — not a single-locale app with i18n plumbing installed and unused. The per-game architecture described in CLAUDE.md delivers on its design.

### Is this "i18n-ready" or just scaffolded?

Ready. Specifically:

- **Pluralization**: CLDR-correct. `pl.json` defines `_one/_few/_many/_other` for every `{{count}}`-interpolated key (e.g. `common.difficultyOfferHeading`, `dashboard.moreTags`, `dashboard.resultsCount`, `gameCard.playCount`); `en`/`es` correctly define only `_one/_other`. i18next's plural resolver is doing real work here, not being bypassed.
- **Interpolation**: Real i18next interpolation (`t('dashboard.titleNamed', { name })` in `src/components/Dashboard.jsx:57`), not string concatenation — see §4 below.
- **Live switching**: Works end-to-end, verified by tracing the mechanism (§5).
- **Locale-aware dates**: Present in two of three date-rendering spots (`ScoreHistory.jsx`, `dateRangeUtils.js`'s month labels) via `Intl.DateTimeFormat(locale, …)`.
- **RTL**: **Not implemented anywhere.** No `dir` attribute is ever set (only `document.documentElement.lang` is synced, in `src/i18n/index.js:58-62`), no CSS logical properties (`margin-inline`, etc.) are used, and no physical-direction CSS was found needing them today (the layout is almost entirely `flex-direction: column`, so it's accidentally RTL-neutral, not deliberately so). This is untested because no RTL locale ships, but it is a real gap that would need work — a `dir` sync alongside `syncHtmlLang`, an audit of the handful of row-flex layouts (nav bar, choice grids, button rows) for logical-property conversion, and icon mirroring where directional (e.g. any arrow icons) — before adding Arabic, Hebrew, or Urdu.
- **Number formatting**: Percentages/scores are rendered as plain template literals (`${v}%`, `${score} / ${total}`) rather than `Intl.NumberFormat`. This is low-risk (digits and `%`/`/` read the same across the shipped locales, and Arabic-indic digit substitution isn't in scope without RTL support anyway) but would need attention alongside RTL work.

## Hardcoded String Findings

Search method: grepped all `.jsx` under `src/` (excluding tests and Storybook stories) for JSX text nodes matching `>word...<`, for literal (non-`{t(...)}`) `aria-label=`, `alt=`, `placeholder=`, and `title=` attribute values, and cross-checked every `.jsx` file for `useTranslation` import coverage. All 9 per-game directories and all 32 non-trivial components/pages import and use `useTranslation`; every game's `manifest.json` uses `nameKey`/`descriptionKey` indirection rather than raw `name`/`description` strings.

## Architecture Assessment

**The per-game i18n architecture works as designed.** Concretely verified:

- `src/i18n/index.js` uses `import.meta.glob('../games/*/i18n/*.json', { eager: true })` to auto-discover every game's locale files with zero registration step, exactly as CLAUDE.md describes. `groupModulesByLocale` + `buildResources` (lines 22-45) assemble one merged resource bundle per discovered locale from core + all games.
- **Namespace collision detection is real, not aspirational**: `mergeLocaleResources` throws (`src/i18n/index.js:12`) if a game's top-level key collides with core or another game — and this is unit-tested (`i18n.test.js`, `mergeLocaleResources` describe block, including the "two game namespaces collide with each other" case).
- **`SUPPORTED_LOCALES` is derived, not hand-maintained** (`src/i18n/index.js:64`) — adding a fourth locale is "drop `xx.json` files," full stop; the admin `LocaleSelector` and the test suite's expectations both consume this dynamically.
- **Indirection via `nameKey`/`descriptionKey`/`labelKey`/`ariaLabelKey` is used pervasively** (manifests, `GameCard.jsx`, `FeaturedGameCard.jsx`, `ReplayButton.jsx`, `Timer.jsx`, `AppShell.jsx`'s route-title map, `GameResults.jsx`'s score-label selection, badge catalogs, item-name catalogs for colors/animals/characters/foods/emotions/sounds). This is why a naive static grep for literal `t('...')` calls produces ~200 "orphan" false positives — spot-checking a representative sample (`shell.navParent`, `kids.title`, `parent.title`, `common.orientationOverlayHeading`, `numberTap.objects.apple`, `color.${id}.name`-style template keys) confirmed every one is genuinely consumed, just one level removed from the literal-string grep. **Real key hygiene is excellent**: 0 genuinely missing keys, 0 genuine orphans found across a full audit of all ~422 unique leaf keys.
- **Locale switching is architecturally correct** (see §5) and reaches permanently-mounted siblings, matching CLAUDE.md's documented broadcast pattern.
- **Speech synthesis is locale-aware by design**, not an oversight-prone add-on: `useSpeech.js` maps `i18n.language` to a BCP-47 voice tag and both call sites (`fruit-veggie-id`, `emotions-match`) speak `t(...)`-translated text, never a hardcoded English word.

**Where it falls short of "fully delivers":**
- The convention is enforced by discipline and tests within `src/games/**` and most of `src/components/**` and `src/admin/**`/`src/parent/**`/`src/kids/**`, but **`src/App.jsx` — the one file outside any per-game or per-feature directory — has four strings that never got wired up** (Finding #1-2). This is the one clear crack in an otherwise very consistent pattern.
- **No RTL support** — the architecture handles *which words* render but not *which direction* they flow, so a right-to-left locale would require additional engineering the current design doesn't yet anticipate (see Locale Coverage above).
- **No lint-level enforcement** against a new hardcoded string being introduced (see §8 below) — the discipline holding so far is convention + code review, not tooling, and `App.jsx`'s misses are the evidence of what happens when a file falls outside habit.

## What's Already Solid

- **Three complete, CI-tested locales** (en/es/pl) across core and all 9 games — not a single-locale skeleton.
- **CLDR-correct pluralization**, including Polish's full four-category system, explicitly unit-tested per pluralizable key (`i18n.test.js`'s `cross-locale key parity` describe block).
- **Automated cross-locale key-parity testing** running in `npm test` / CI — this is a genuinely uncommon level of i18n test discipline for a project this size and directly satisfies the "build-time validation" ask in a way most apps lack.
- **Locale-aware speech synthesis** (`useSpeech.js`) mapping locale → correct voice language tag, with graceful `supported`/`blocked` fallback for browsers/environments (jsdom, blocked-autoplay) without Speech API support.
- **Correct i18next interpolation** for dynamic content (child's name, badge counts, scores) — no manual string concatenation found anywhere in the audited surface (`t('dashboard.titleNamed', { name })`, `t(scoreLabelKey, { score, total })`, `t(ariaLabelKey, { seconds })`, badge/plural counts all use `{{}}` interpolation properly).
- **Namespace-collision detection with test coverage**, preventing a silent key clash between two games or a game and core as the codebase grows.
- **`SUPPORTED_LOCALES` derived from discovered files, not a hardcoded list** — genuinely zero-config to add a locale from the resource-bundling side.
- **Locale-neutral audio asset choice**: the animal-sounds and sound-memory-match games use real recorded animal sound effects (a cat's meow sounds the same in every language) rather than spoken English words, sidestepping the audio-localization problem entirely for those games — the right call, not an oversight. Only two games use spoken TTS prompts, and both correctly localize them.
- **`html lang` kept in sync** with the active locale (`src/i18n/index.js:58-62`), both at init and on every language change — good for screen readers and browser-level language detection.

## Recommendations (Prioritized)

1. **[High]** Fix `src/App.jsx`'s four hardcoded strings (Findings #1, #2) — add `common.gameNotFound` and `common.loading` (or reuse an existing loading key if one exists in a game) to `src/i18n/{en,es,pl}.json`, and route the Suspense fallbacks and the not-found div through `t()`. These are the highest-traffic untranslated strings in the app precisely because they're structural, not content.
2. **[Medium]** Fix the parent dashboard's chart date formatting (Finding #5) to use `Intl.DateTimeFormat(i18n.language, …)`, matching the pattern already correctly used two sections below it in the same file.
3. **[Medium]** Add an ESLint rule (e.g. `eslint-plugin-i18next`'s `no-literal-string`, scoped to `src/**/*.jsx` with a tuned allowlist for CSS-only glyphs, test IDs, and the CSV header case) to `eslint.config.js` so a future `App.jsx`-style miss fails CI instead of shipping. This is the one layer of validation the project's otherwise-strong test discipline doesn't cover.
4. **[Low]** Fix `ScoreHistory.jsx`'s fallback date path (Finding #4) to pass `i18n.language` for consistency, even though it's effectively unreachable given the current score-shape contract.
5. **[Low, only if a 4th locale is planned]** If any RTL locale (Arabic, Hebrew, Urdu, etc.) is ever on the roadmap, budget real design/engineering time for it — it's not a drop-in the way `es`/`pl` were. Needed: a `dir` sync alongside the existing `syncHtmlLang`, conversion of the handful of row-flex layouts (nav, choice grids, button rows) to CSS logical properties, and an icon/glyph audit for anything directional (none found today, but worth re-checking at that time).
6. **[Low]** Consider whether percentage/score number formatting (`${v}%`, `${score} / ${total}`) should move to `Intl.NumberFormat` — low urgency for the currently-shipped locales (Latin-script, Western-Arabic-numeral locales all render digits identically) but worth revisiting alongside RTL work if a locale with different numeral systems is ever added.

## Other Areas Noticed (Non-i18n, Cross-Cutting)

- **`src/App.jsx`'s inline `style={{ padding: 24 }}` on loading/error fallbacks** bypasses the project's own CSS-custom-property design-token convention (CLAUDE.md: "use `var(--color-aqua)` etc. rather than hardcoding hex values... so games stay visually consistent") — while padding isn't a color token, these four spots are also the only inline-styled, non-componentized UI surface found in an otherwise consistently componentized app. Worth a look alongside the i18n fix since it's the same four lines.
- **`GAME_ITEM_NS` in `src/parent/ParentDashboard.jsx:39-42`** (`{ 'animal-sounds': 'animal', 'color-match': 'color' }`) is a hardcoded map from two specific game IDs to their item-name i18n namespace. It's not an i18n *string* problem, but it is a manually-maintained mapping that will silently miss any future "identify an item and see stats per item" game unless someone remembers to add an entry here — worth a comment pointing future contributors at it, or deriving it from each game's manifest instead.
- No `ErrorBoundary` component was found anywhere in `src/` (searched by filename pattern) — an uncaught render error in any game would presumably produce React's default white-screen/console-only failure rather than a user-visible (and translatable) fallback. Outside this audit's scope but adjacent to Finding #1/#2's "what does the user see when something goes wrong" theme.

*Methodology note: locale key coverage and cross-locale diffs were computed by flattening every `en.json`/`es.json`/`pl.json` to leaf paths and comparing sets programmatically (not sampled). The "used vs. defined key" cross-check initially produced ~200 false-positive "orphans" due to pervasive `nameKey`/`descriptionKey`/template-literal key indirection (e.g. `` `animal.${id}.name` ``); each pattern was traced to a real call site before being excluded.*
